# `auth_type` in the IR — implementation plan

Plan readiness: ready.

## Outcome and scope

Add an optional provider-level `auth_type` to the IR that selects how the
credential is presented to the upstream, and document which upstream uses
which mechanism.

- Values: `official` (default), `bearer`, `x-api-key`, `none`.
- Requested because the pi-derived targets (pi, prime-agent) reject
  `Authorization: Bearer ENV:NAME` with no alternative, so a gateway that
  wants bearer auth cannot be generated at all (reported "连不上").
- Exclusions: MCP-server auth is unchanged (`Bearer ENV:` keeps working
  there). No new `auth_type` mapping for targets outside the pi family; they
  must report a diagnostic instead of ignoring it. Not fixing the separate
  `contextWindow: 0` / `maxTokens: 0` sentinels in the pi emitter.

Existing changes: none (tree clean at `3db170e`).
Authorization: implementation — user chose the value set and asked for the docs.

## Design and constraints

Verified upstream facts (source, not docs):

- pi `packages/coding-agent/src/core/provider-composer.ts:274-286` —
  `authHeader: true` adds `Authorization: Bearer <resolved apiKey>` and throws
  `authHeader requires a resolved API key` when the key is unresolved.
- pi `packages/ai/src/api/openai-completions.ts:787` — `new OpenAI({ apiKey })`,
  so the OpenAI transports default to `Authorization: Bearer`.
- pi `packages/ai/src/api/anthropic-messages.ts:979-981` — the normal path is
  `new Anthropic({ apiKey, authToken: null })` → `x-api-key`. Bearer is used
  only for `provider === "github-copilot"` and OAuth `sk-ant-oat` tokens.
- omp `models-config-schema-bundle.ts` — provider carries `auth:
  "apiKey" | "none" | "oauth"` + `authHeader: boolean`, and rejects
  `apiKey: ""` (`mustBe("apiKey a non-empty string")`). prime-agent is a pi
  fork with the same `authHeader` schema and Bearer injection
  (`model-registry.ts:202`, `:1561`).

Semantics: `auth_type` is orthogonal to `protocol`; it overrides the
credential-injection default of the selected protocol. `official` means
"target/protocol native" and is a no-op, so existing configs keep working.

IR contract and invariants:

- `auth_type` is parsed with `KnownFields(true)`; an unknown value is an error.
- `bearer` / `x-api-key` require `api_key` to be present (`Value` or `FromEnv`).
- `none` forbids `api_key`.
- `official` adds no constraint.
- A target that does not implement the mapping must emit a diagnostic for any
  non-`official` value — the emitter contract forbids silently dropping meaning.

Target mapping (pi family):

| `auth_type` | pi / prime-agent |
| --- | --- |
| `official` | native `apiKey` as today |
| `bearer` | native `apiKey` + `authHeader: true` |
| `x-api-key` | accepted only for `protocol: anthropic-messages` (already the native default); diagnostic on the OpenAI protocols, whose transport always authenticates with Bearer |
| `none` | omit the native `apiKey` field entirely |

Omitting `apiKey` also removes the current `apiKey: ""` emission, which omp
rejects at schema validation and pi turns into `No API key for provider`.

Capability plumbing: `target.AuthTypeValidator` is an optional interface.
Targets implementing it own representability; the default path (all other
targets) diagnoses every non-`official` value. The check is invoked from
`app.runTargetValidation` so `validate` and `gen` agree.

Upstream reference table (docs deliverable; pi/OpenAI rows are source-verified,
gateway rows are convention):

| Upstream | Protocol | Native auth | `auth_type` |
| --- | --- | --- | --- |
| Anthropic official | `anthropic-messages` | `x-api-key` | `official` |
| OpenAI official | `openai-completions` / `openai-responses` | `Authorization: Bearer` | `official` |
| OpenRouter | `openai-completions` | `Authorization: Bearer` | `official` |
| new-api / one-api (fronting Claude) | `anthropic-messages` | gateway wants Bearer | `bearer` |
| new-api / one-api (fronting GPT) | `openai-completions` | `Authorization: Bearer` | `official` |
| LiteLLM / Vercel AI Gateway | `openai-completions` | `Authorization: Bearer` | `official` |
| Ollama / LM Studio / llama.cpp / vLLM | any | no credential | `none` |

#### T2a: share the pi-family document builder (agreed with the user)

The first pass wrote the same mapping rules into both emitters. Because the
forks are one codebase and a third (Oh My Pi) is coming, the rules now live in
`internal/target/pifamily`, parameterised by the three things the forks actually
differ on: file path, encoding, and credential value syntax
(`DollarEnv` for pi's `"$NAME"` template, `BareEnv` for the bare
environment-variable name that Prime Agent and Oh My Pi resolve). Two rules that
were identical in both files moved with it: the literal-expression rejection and
the text/image input limit.

Switching pi to the builder also changed its artifact from a TypeScript provider
extension to `~/.pi/agent/models.json`, which is what upstream documents for
custom providers. That removed the `apiKey: ""` and `contextWindow: 0` /
`maxTokens: 0` sentinels; unset limits are now omitted so the fork's defaults
apply.
